# Маркетплейс — требования безопасности и проверка перед релизом

ТЗ «Команда — маркетплейс SavdEx» от 18.11, раздел 11.4 (безопасность).
Что уже есть в коде, держат тесты (`tests/test_market*.py`); здесь —
правила для частей, которых ещё нет (заказ, оплата, склад, касса), и
список, который проходим перед каждым релизом маркетплейса на боевой.
Пишешь заказ, оплату, склад или кассу — каждое правило ниже должно
держаться кодом и тестом, не договорённостью.

Подробности найденных и ещё не закрытых дыр сюда не пишем — репозиторий
публичный; они в закрытой базе команды («Проверка безопасности SavdEx»).

## 1. Корзина и заказ

**Цена — только с сервера.** Уже так: в корзине — номер варианта и
количество, цена каждый раз из `market_product_variants`
(`market/cart.py`). При оформлении:
- сумма пересчитывается из базы в той же транзакции, что создаёт заказ;
  клиент присылает сумму, которую видел (`expectedTotal`), — не совпала
  (продавец поменял цену) — 409 и новая корзина, а не заказ по новой цене;
- в позицию заказа копируются цена, название, ИКПУ и процент комиссии на
  момент покупки; дальше заказ живёт на копии;
- сумма счёта Uzum — только из заказа, никогда из запроса.

**Последняя штука — одному.** Резерв — одним условным обновлением на
позицию, в одной транзакции на весь заказ:

```sql
update market_product_variants set reserved = reserved + %(n)s
where id = %(id)s and is_active and stock - reserved >= %(n)s
returning id
```

Не обновилась хоть одна строка — откат всего заказа. Позиции — по
возрастанию `id` (без взаимных блокировок). База держит
`stock >= 0` и `0 <= reserved <= stock` — это последняя линия, а не
проверка. Отмена и истечение неоплаченного заказа снимают резерв ровно
один раз: переход статуса — `update … where status = <ожидаемый>`, ноль
строк — уже сделано. Форма остатка в админке: меньше резерва — понятная
ошибка, не 500.

**Чужой заказ по номеру.** Каждый запрос заказа — с владельцем в
условии: покупателю — `where buyer_user_id = <из сессии>`, продавцу —
только его часть (`where seller_id = …`), без телефона покупателя
(раздел 4 ниже). Номер наружу — непоследовательный (случайный код), не
`id` и не время. Не своё — 404, а не 403: существование чужого заказа не
подтверждаем.

**Код выдачи.** 6 цифр; в базе — только отпечаток (HMAC с ключом
приложения), открытым код не хранится нигде, в уведомлении его нет;
показывается покупателю в его заказе со статуса «можно забрать». Сделано
(`savdex/market/warehouse.py`): код не из `secrets`, а выводится HMAC из
ключа приложения, номера заказа и времени прихода — так его можно
показать покупателю, не храня открытым; без ключа приложения ни код, ни
отпечаток не подобрать. Проверка — только в паре «заказ + пункт
выдачи» (сотрудник видит и отмечает только заказы своего пункта), не по
одному коду. Неверный код: не больше 5 попыток на заказ, дальше ввод
закрыт до звонка — открывает администратор с причиной («Открыть ввод
кода выдачи» в карточке заказа); у сотрудника ПВЗ — свой счётчик, 20
неверных кодов в час по всем заказам (`savdex/web/throttle.py`). Каждая
выдача и каждая неудачная попытка — в журнал действий (без самого кода).

## 2. Товары

Уже так и должно остаться:
- фото — тип по содержимому (Pillow: JPEG, PNG, WebP), не по имени и не
  по MIME из запроса; ≤ 8 МБ, ≤ 48 Мп до распаковки; всегда пересборка в
  WebP без EXIF, случайное имя (`savdex/images.py`); SVG и HTML не
  проходят; не больше 10 фото — под блокировкой товара;
- описание и названия — текст: на сайте — текстовым узлом React, в
  админке — `format_html` с подстановкой. `dangerouslySetInnerHTML` и
  `mark_safe` для текста продавца — нельзя.

Появится JSON-LD или `og:*` с текстом товара — `json.dumps` и замена
`<` на `<`; станет описание Markdown или HTML — очистка на сервере
по белому списку тегов.

## 3. Деньги

**Колбэки Uzum** (образец — `web/payment_callbacks.py`, уже так):
Basic с `hmac.compare_digest`, повтор транзакции отсекает уникальность
`(provider, provider_transaction_id)`, `confirm`/`reverse` — под
`FOR UPDATE`, сумма сверяется с базой, телу вебхука сумма не доверяется,
зачисление — один раз (`web/settlement.py`). Для маркетплейса — то же
плюс:
- отдельный терминал (`serviceId`) — оплаты не смешиваются с тарифами;
  на боевом `serviceId` и список адресов Uzum заданы обязательно;
- один живой счёт на заказ: уникальность `order_id` среди оплат в
  статусах «ожидает» и «оплачен»; вторая оплата того же заказа — отказ
  и возврат, а не второе зачисление;
- обработка вебхука — в транзакции целиком: двойной одновременный
  вебхук — второй видит готовое, а не 500.

**Отмена после оплаты.** Оплаченный картой заказ при отмене переходит в
«ожидает возврата», не сразу в «отменён»; возврат — через API Uzum, один
раз (переход статуса с условием); ответ Uzum — в журнал денег. Отмена
покупателем — только до отгрузки со склада (ТЗ, раздел 7).

**Журнал денег.** Записи только дописываются: у роли приложения на
таблицу нет `UPDATE` и `DELETE` (или триггер-запрет); каждое движение —
набор записей с суммой ноль; суммы — целые тийины. Ночная сверка: журнал
сходится в ноль, оплаты = реестр Uzum, наличные = отчёт BTS; расхождение
— тревога в Telegram.

**Выплаты продавцам** — только роль кассы, в два шага: один сотрудник
создаёт, другой подтверждает (не тот же). Каждое действие —
`audit.record` (кто, что, сумма, продавец). Реквизиты продавца меняются
только с записью в журнал; выплата на реквизиты, сменённые меньше суток
назад, — только после повторного подтверждения.

## 4. Роли админки

Раздел — `savdex/access.py`, права модели в админке — по разделу, к
которому она привязана (`register(..., section=…)`); инлайн без своего
раздела задаёт права сам (`market/admin.py`, `VariantInline`).

| Роль | Видит | Не видит |
|---|---|---|
| модератор | продавцы, товары, их решения | деньги, выплаты, склад |
| склад (`warehouse`, раздел `market_stock`) | поставки, приёмка, отгрузки, движения остатка — только своего склада | деньги, продавцов, решения модерации, выдачу |
| пункт выдачи (`pickup_point`, раздел `market_pickup`) | заказы и отгрузки своего пункта, выдача по коду, «к оплате» у заказа при получении | другие пункты, остальные суммы, склад |
| касса (`cashier`, раздел `market_cash`) | оплаты, начисления, выплаты, сверка | правку заказов и остатков |
| поддержка | заказы и продавцы — только смотреть | суммы (`_DETAILS_HIDDEN`), выплаты |

Остаток в админке — только смотреть: он приходит с приёмки и меняется
движениями склада с причиной (`savdex/market/warehouse.py`). Тест прав (`tests/test_access_parity.py`, `tests/test_market.py`)
проверяет и «чего нет»: у модератора и поддержки нет `market_cash.*`, у
кассы нет `market.edit` и `market_stock.edit`.

## 5. Персональные данные (ТЗ, раздел 10)

- Телефоны, имена, данные OneID покупателей и продавцов — только в нашей
  базе в Узбекистане. Не в журналах (ни приложения, ни Actions), не во
  внешних сервисах: аналитика, мониторинг, Telegram-тревоги — только
  цифры и номера записей.
- Из OneID (`market/oneid.py`) храним минимум: совпавший ИНН компании,
  время, HMAC от ПИНФЛ (ключ `ONEID_PIN_KEY`); ФИО, паспорт, адрес, дату
  рождения — нигде, даже в сессии. ТЗ разрешает ФИО и название
  организации — не берём, пока не понадобятся.
- Продавцу о покупателе — имя и номер заказа; телефона нет (выдаёт ПВЗ).
  API продавца — отдельный сериализатор, а не «весь заказ».
- Документы продавца — в одном месте (`company_documents`), своих копий
  маркетплейс не хранит.
- Выгрузки и ответы API — без лишних полей: новое поле с персональными
  данными в ответе — только с тестом, что чужому его не видно.

## 6. Проверка перед каждым релизом маркетплейса

Проходит тот, кто готовит релиз, вместе с отвечающим за безопасность
(Жавохир); отметка — в заметке релиза в базе команды. Не прошёл пункт —
релиза нет.

**Код и CI**
- [ ] «CI» зелёный на коммите-кандидате; тесты маркетплейса не
      пропущены и не отключены (`pytest -rs` — без skip в `test_market*`).
- [ ] Библиотеки: `pip-audit` и `npm audit` — нет уязвимостей high и
      critical (или есть решение, почему можно).
- [ ] В диффе от прошлого релиза — ни секретов, ни адресов сигналов, ни
      персональных данных (`git diff <прошлый>..<кандидат>`).
- [ ] Новые адреса `/market/api/…`: у записи — CSRF и ограничение
      частоты; у чтения своего — владелец в условии запроса; тест на
      «чужое — 404».

**Деньги и остатки** (когда есть)
- [ ] Тест «последняя штука двоим» и «двойной вебхук» зелёные.
- [ ] Сумма счёта — только из заказа; повтор `transId` — отказ.
- [ ] Ночная сверка на тестовом сошлась в ноль за последние сутки.

**Настройки боевого**
- [ ] `MARKET_DOMAIN` в разрешённых хостах; кука сессии — общая только
      для основного адреса и маркетплейса (решение о тестовом и превью —
      в базе команды).
- [ ] Uzum маркетплейса: свой `serviceId`, список адресов Uzum задан.
- [ ] OneID: `ONEID_*` заданы в окружении `production`, адрес возврата —
      https на адресе с кнопкой; ключ `ONEID_PIN_KEY` не менялся (иначе —
      пересчёт).
- [ ] Права ролей: на тестовом под модератором, складом, кассой и
      поддержкой открыть каждый раздел маркетплейса — каждый видит только
      своё.

**После выкладки**
- [ ] Проверка снаружи прошла; в журналах первого часа нет 5xx на
      `/market/…` и нет персональных данных.
- [ ] Строка в журнал месяца в базе команды и отметка в ТЗ.
