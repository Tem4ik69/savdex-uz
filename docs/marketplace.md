### Главные правила (держит код и сама база)

- **Деньги — целыми тийинами** (`bigint`, 1 сум = 100 тийин). Наружу
  цены уходят в сумах. Цена больше нуля, старая — больше новой.
- **Покупателю виден только товар «в продаже»** у подтверждённого
  продавца с живой компанией. Черновик, отклонённый, снятый товар и
  товары заблокированного продавца — 404 и по прямой ссылке.
- **Остаток продавец не задаёт**: по ТЗ к продаже — только то, что на
  складе BTS. Пока склада в коде нет, остаток ставит сотрудник в админке
  (Маркетплейс → Товары → варианты). Остаток и резерв не уходят в минус,
  резерв не больше остатка — ограничения в таблице.
- **В продаже — только с ценой, адресом и ИКПУ** (ИКПУ нужен для чека).
- Пока продавец «новый», правка текста, категории, характеристик или фото
  возвращает товар в черновик — на повторную проверку. Цена и варианты
  статус не меняют.
- **Документы продавца — не копируются**: модератор смотрит документы
  компании в разделе «Документы на проверку». Персональные данные — в
  одном месте, в Узбекистане.

### Схема — что решили при сверке 19.11 (Нозим и Шерзод)

- Продавец — компания (`company_id` уникальный), заявку подаёт владелец;
  документы — в `company_documents`, своих копий нет.
- У каждого товара хотя бы один вариант: цена и остаток — у варианта.
  В строке товара — сводка (самая низкая цена, её старая цена, остаток)
  для сортировки и фильтров; пересчитывает `products.py`.
- Глубину категории не храним (разошлась бы с деревом при переносе), до
  трёх уровней держит админка. Товар — в любой категории без подразделов.
- Счётчик «первых N» — запросом по `approved_at`, не хранимым числом.
- «Новинка» — по `published_at`.
- Адрес товара — `slug` с номером в конце, не меняется при
  переименовании, не переходит к другому товару.
- Фото — общее или одного варианта (`variant_id`, только этого же товара;
  убрали вариант — фото остаётся общим), с уменьшенной копией
  `thumb_path` для каталога на телефоне.
- Поиск — по началу слова, словарь `simple`, в самом PostgreSQL. Ничего не
  нашёл — те же фильтры, но по похожему написанию названия (`pg_trgm`,
  миграция `2026_11_19_120000_add_typo_search_to_market.sql`): «смартфн» →
  «Смартфон», «samsng» → «Samsung»; в ответе каталога — `fuzzy: true`, чтобы
  страница написала «показаны похожие». Подсказки — так же. Порог похожести
  0.5 — настройка базы (по умолчанию у `pg_trgm` 0.6 — «samsng» не нашлось
  бы). Расширение ставит владелец базы (`savdex`) — на боевой базе он
  суперпользователь, проверено 19.11. Латиница и кириллица («ксиоми» →
  «Xiaomi») триграммами не связываются — отдельная задача.
- Перевод текста товара — вопрос ТЗ (№ 10); если делать — вторым этапом и
  после маскировки контактов в описании.
- Схему меняем только добавлением: новые столбцы пустые по умолчанию, чтобы
  прежний код на машине сайта не ломался во время релиза.

## Заказ — этап 1

Код — `python/savdex/market/orders.py`, схема —
`2026_11_21_100000_create_market_orders.sql`, проверки —
`python/tests/test_market_orders.py`. Правила — `docs/marketplace-security.md`
(разделы 1, 3, 5).

- **Оформление** (`POST checkout`): пункт выдачи (пока Ташкент; таблица
  `market_pickup_points`, пункты заводит администратор в «Маркетплейс →
  Пункты выдачи» — список BTS не решён) и способ оплаты (`card` — картой на
  сайте, `cash` — при получении) → **один заказ** с **частями по
  продавцам** (`market_order_parts`: у каждого продавца своя сумма и
  комиссия). Номер заказа — случайный код из 10 знаков, не `id`.
- **Цена и остаток — только из базы**, в той же транзакции. Браузер шлёт
  сумму, которую видел (`expectedTotal`, в сумах): не совпала — `409` и
  свежая корзина (`cart`). В заказ идёт то, что корзина считает «можно
  купить сейчас»; прочие строки остаются в корзине (куплено меньше, чем
  лежало, — остаток строки тоже остаётся). В позицию копируются
  цена, название, выбор, ИКПУ и процент комиссии (настройка
  `market_commission_percent`, по умолчанию 10).
- **Резерв** — одним условным обновлением на вариант, по возрастанию номера:
  не хватило хоть одного — откат всего заказа, `409` «Товар закончился».
  Сводка остатка товара (`market_products.stock`) пересчитывается в той же
  транзакции — и при оформлении, и при снятии резерва. Порядок блокировок
  везде один: сначала строки товаров (по возрастанию), потом варианты.
- **Незавершённых заказов** (`created`, `cash_on_pickup`, плюс отменённые
  самим покупателем за последние сутки) у покупателя — не больше 5: шестое
  оформление — `409`. Заказ с оплатой при получении,
  который за 48 часов (настройка `market_cash_order_expire_hours`) не начали
  собирать, отменяется сам — тем же путём, что отмена покупателем.
- **Статусы**: `created` (ждёт оплаты картой) → `paid` / `cash_on_pickup` →
  `assembling` → `in_transit` → `ready` → `issued`; плюс `cancelled`,
  `refund_pending`, `refunded`. Меняет только `orders.transition` —
  `update … where status = ожидаемый`; история — `market_order_events`.
- **Отмена** покупателем — до `in_transit`; оплаченный картой — в
  `refund_pending`. Резерв снимается ровно один раз
  (`reserve_released_at`). Неоплаченный картой заказ старше 30 минут
  (настройка `market_order_expire_minutes`) отменяется сам: расписание
  каждый час (чаще расписание не умеет) и `manage.py market_expire_orders`.
  Продавцу неоплаченный картой заказ не виден ни до оплаты, ни после отмены.
- **Журнал денег** `market_ledger` — двойная запись: группа строк с суммой
  ноль (`orders.post`, триггер `market_ledger_balanced` в конце транзакции),
  только дописывается (у роли приложения нет `update`/`delete`/`truncate`,
  `update` и `delete` триггер запрещает и владельцу; `truncate` у владельца оставлен для очистки баз проверок). Счета: `buyer_receivable` (покупатель заплатит при
  получении), `gateway_clearing` (деньги у Uzum), `cash_collected` (наличные
  в ПВЗ, этап кассы), `seller_payable` (должны продавцу, с `seller_id`),
  `commission_revenue` (комиссия), `refund_payable` (вернуть покупателю),
  `delivery_revenue` (доставка, когда она появится в заказе).
  При получении — начисление сразу при оформлении; картой — когда пришли
  деньги (`orders.mark_paid`).
- **Админка**: «Маркетплейс → Заказы» (раздел `market_orders`; поддержка —
  только смотреть, без сумм). Администратор (`market_orders.moderate`)
  двигает заказ кнопками в карточке: в сборку (из `paid` и
  `cash_on_pickup`) → отгружен → в пункте → выдан, а заказ с оплатой при
  получении может отменить до отгрузки (резерв и обратная проводка — общим
  путём отмены), оплаченный картой — тоже, в «ожидает возврата». Выдача
  (`issued`) в той же транзакции списывает остаток и резерв позиций ровно
  один раз (`stock_written_off_at`) и растит продажи товара. Каждое действие — строка журнала действий. «Пункты
  выдачи» — администратор.

| Адрес | Что |
|---|---|
| GET `pickup-points` | `{pickupPoints: [{code, name, address, city}]}` |
| POST `checkout` `{pickupPoint, paymentMethod, expectedTotal}` | `201 {order}`; ошибка поля — 422, сумма или остаток изменились — `409 {message, cart}`, уже 5 незавершённых заказов — `409 {message}` |
| GET `orders` | свои заказы: `{orders: [{number, status: {code, text}, total, count, pickupPoint, createdAt}]}` |
| GET `orders/<номер>` | свой заказ: части по продавцам, позиции, `canCancel`; чужой — 404 |
| POST `orders/<номер>/cancel` `{reason?}` | отмена; после отгрузки — 409 |
| GET `me/orders` | продавцу — только его части: номер, статус, имя покупателя (без телефона и почты), позиции, сумма, комиссия, `payout` |

**Этап 2 (оплата Uzum)** зовёт: `orders.mark_paid(order_id, amount)` —
сумма сверяется с заказом, `created → paid` и начисление
(`gateway_clearing`); `False` — уже оплачен, отменён по сроку или сумма не та
(деньги — назад); `orders.mark_refunded(order_id)` — `refund_pending →
refunded` и закрытие долга покупателю. Код выдачи (`pickup_code_hash`) — с
этапом ПВЗ.

## Оплата — этап 2

Код — `python/savdex/market/payments/` (`base.py` — общий слой, `uzum.py`,
`payme.py`, `click.py`, `reconcile.py`), схема —
`2026_11_21_110000_create_market_payments.sql`, проверки —
`python/tests/test_market_payments.py`. Правила —
`docs/marketplace-security.md`, раздел 3.

- **Счёт**: `POST orders/<номер>/pay {provider: uzum | payme | click}` →
  `{provider, redirect}` — адрес страницы оплаты провайдера. Только свой заказ
  (чужой — 404), только `card` и только `created`; оплачен — 409, оплата уже
  идёт у провайдера — 409, провайдер выключен или неизвестен — 422. Повтор —
  тот же счёт; смена провайдера гасит прежний не начатый счёт.
- **Одна живая оплата на заказ** (`market_payments`: `created` — счёт открыт,
  `pending` — провайдер завёл транзакцию, `paid`, `cancelled`, `refunded`) —
  держит и база: уникальный индекс по `order_id` среди `created/pending/paid`;
  повтор транзакции — уникальность `(provider, provider_transaction_id)`.
- **Сумма — только из заказа**, колбэк сверяет присланную. Проведение —
  `orders.mark_paid` под замком заказа (порядок замков везде: заказ, затем
  оплата). Заказ уже не ждёт оплаты (отменён, истёк) — ошибка провайдеру на
  любом шаге, включая проведение (Payme Perform → -31008, Click Complete →
  -9, Uzum confirm → 10009): провайдер гасит платёж и возвращает деньги, у
  нас ничего не начислено; у оплаты — `rejected_at` (`base.reject`) во всех
  ветках «провайдер пришёл проводить, мы отказали», в том числе по
  транзакции, погашенной раньше (брошенная попытка, истёк срок), — и сверка
  просит проверить, что провайдер деньги вернул. Заказ, по которому провайдер завёл
  транзакцию, `expire` не отменяет, пока она моложе отсрочки — максимума из
  `market_order_expire_minutes` и сроков pending провайдеров; условие
  перепроверяется под замком заказа.
- **Брошенная попытка** Uzum или Click (pending старше
  `MARKET_UZUM_CONFIRM_TIMEOUT` / `MARKET_CLICK_PENDING_MINUTES`, по
  умолчанию 30 минут) заказ не держит: новая попытка или счёт со страницы её
  гасят. У Payme свой срок — 12 часов, отменяет он сам.
- **Колбэки** — сервер серверу, вне CSRF (`csrf_exempt`; проверка CSRF
  Django и так стоит только на `/py/`), под подписью или паролем
  (`hmac.compare_digest`), каждый — одной транзакцией. Только у провайдера с
  ключами — иначе 404. **Новые транзакции** (Uzum `check`/`create`, Payme
  `CheckPerformTransaction`/`CreateTransaction`, Click Prepare) — только где
  маркетплейс открыт (`market_open()`; на боевом пока — 404). **По уже
  заведённым** (confirm, reverse, status, Perform, Cancel, Check,
  GetStatement, Complete) провайдер достучится всегда: колбэки — вне
  обёртки `_open_only` в `market/urls.py`, иначе деньги повисли бы при
  закрытии маркетплейса.
- **Белый список адресов** — `MARKET_<ПРОВАЙДЕР>_CALLBACK_IPS` (через
  запятую); на боевом обязателен у всех трёх, без него провайдер выключен.
- **Лимиты** (файловый кэш, `savdex/web/throttle.py`): не больше
  `MARKET_CALLBACK_RATE` (120) колбэков в минуту с адреса и не больше
  `MARKET_CALLBACK_AUTH_FAILS` (10) неудачных проверок подписи или пароля за
  10 минут — дальше отказ в формате провайдера. Только для адресов **не** из
  списка провайдера: если список задан (на боевом — всегда), запросы с
  чужих адресов и так отклоняются, а свои лимитами не режутся, неудачная
  подпись с адреса провайдера — только WARNING в журнал. Кэш не файловый —
  считать негде: WARNING один раз (только на боевом). Плюс общий счётчик
  неудачных проверок у провайдера со всех адресов: 10 за 10 минут — ERROR
  «много неудачных проверок колбэка <провайдер>» один раз за окно (подбор
  ключа или сбитые ключи у самого провайдера).
- **Кривые значения** при верной подписи — отказ провайдеру, не 500: суммы —
  только цифры ASCII в пределах bigint, `reason` Payme — smallint, `from`/`to`
  — bigint, переполнение Decimal у Click — «сумма не та»; эхо в ответах —
  только строки до 64 знаков. Повтор Payme Create или Click Prepare с
  известным id сверяет заказ, сумму и что заказ всё ещё ждёт оплаты.

| `MARKET_PAYME_PENDING_MINUTES`, `MARKET_CLICK_PENDING_MINUTES` | срок pending для отсрочки истечения и брошенных попыток (по умолчанию 30; потолок — Payme 720, Click 1440) |
| `MARKET_CALLBACK_RATE`, `MARKET_CALLBACK_AUTH_FAILS` | лимиты колбэков с адреса (120 в минуту, 10 неудач за 10 минут) |
| `MARKET_DELIVERY_IKPU` | ИКПУ доставки для чека Payme (когда `delivery_total > 0`) |
| `MARKET_HC_PING_PAYMENTS` | Ping URL проверки Healthchecks для ночной сверки — секрет GitHub, релиз пишет его в `signals.env` машины админки (`docs/monitoring.md`) |
| `MARKET_PAYME_MERCHANT_ID`, `MARKET_PAYME_KEY` | касса и ключ (Basic `Paycom:<KEY>`) |
| `MARKET_PAYME_CHECKOUT_URL` | по умолчанию `https://checkout.paycom.uz` (песочница — `https://checkout.test.paycom.uz`) |
| `MARKET_PAYME_ACCOUNT_FIELD` | поле `account` (по умолчанию `order`) |
| `MARKET_CLICK_SERVICE_ID`, `MARKET_CLICK_MERCHANT_ID`, `MARKET_CLICK_SECRET_KEY` | сервис, поставщик и ключ подписи |
| `MARKET_CLICK_MERCHANT_USER_ID` | для возврата через Merchant API Click (необязательно) |
| `MARKET_CLICK_PAY_URL`, `MARKET_CLICK_API_URL` | по умолчанию `https://my.click.uz/services/pay` и `https://api.click.uz/v2/merchant` |
| `MARKET_PAYMENT_RETURN_URL` | куда вернуть покупателя, `{number}` — номер заказа; по умолчанию страница заказа; с `;` или `=` не берётся (ломает ссылку Payme) |

**Сроки pending** (`MARKET_UZUM_CONFIRM_TIMEOUT`, `MARKET_PAYME_PENDING_MINUTES`,
`MARKET_CLICK_PENDING_MINUTES`) должны **совпадать на машинах сайта и
админки**: брошенные попытки гасит сайт (колбэки и счёт), отсрочку истечения
заказа считает админка (расписание). Разные значения — заказ истечёт под
идущей оплатой или будет ждать дольше нужного.

НДС в чеке Payme — настройка `market_vat_percent` (по умолчанию 12). Чек с
пустым кодом не отправляем: у позиции нет ИКПУ (или у доставки —
`MARKET_DELIVERY_IKPU`) — Payme получает отказ -31054 ещё до транзакции.

**Возврат** (`base.refund_order(order_id)`, расписание `market_refunds` —
каждый час): только заказ в `refund_pending`; запрос — ровно один раз
(`refund_requested_at`), `paid → refunded` и `orders.mark_refunded` — одной
транзакцией.

- **Uzum**: продавец вернуть запросом не может — отмена транзакции в кабинете
  Uzum, Uzum зовёт `reverse`; проведённую принимаем, только если заказ ждёт
  возврата (иначе 10017).
- **Payme**: так же — отмена в кабинете Payme Business, Payme зовёт
  `CancelTransaction` (состояние -2); заказ не ждёт возврата — -31007.
- **Click**: reversal через Merchant API, если задан
  `MARKET_CLICK_MERCHANT_USER_ID`; иначе — вручную в кабинете Click.
- Где API нет — в истории заказа пометка администратору (что сделать в
  кабинете), заказ остаётся `refund_pending`, пока не придёт отмена от
  провайдера.
- Провайдер выключен (нет ключей) — отметку «запрошен» не ставим
  (`disabled`), расписание повторит после включения. Провайдер вернул через
  API, а заказ отметить не удалось (`unrecorded`) — ERROR с номером оплаты,
  сверка показывает.

**Сверка** — `manage.py market_reconcile_payments [--day ГГГГ-ММ-ДД]` и
расписание каждую ночь (02:40 UTC, за вчера): по каждому провайдеру деньги у
провайдера по журналу (`gateway_clearing`) = сумма проведённых оплат, статусы
заказа и оплаты согласованы, «возврат запрошен, а заказ уже не ждёт
возврата»; оплаты, отклонённые на проведении (`rejected_at`), — «проверить
возврат у провайдера»; выписка провайдера — где есть API (сейчас ни у
одного: у Payme реестр — наш же ответ `GetStatement`); группы журнала за день
в ноль; заказы, которые ждут возврата дольше `market_refund_alert_hours`
(настройка, по умолчанию 24 ч). Расхождение — ERROR в журнале приложения
(только счётчики) и код выхода 1; номера заказов и оплат — только в вывод
команды. Непроверенные отказы на проведении сверка напоминает каждую ночь,
пока сотрудник не отметит проверку у провайдера: `base.acknowledge(payment_id,
admin_user_id, note)` или `manage.py market_ack_payment <оплата> --admin <id>
--note "<текст>"` — только сотрудник с правом `market_cash.moderate` или
суперадмин, заметка не короче 10 знаков; пишет `rejection_checked_at`,
`checked_by`, `check_note`, журнал действий админки (`payment_checked`,
раздел `market_cash`) и пометку в истории заказа от имени сотрудника. Так же
снимается зависший возврат — отметкой на самой оплате возврата (`paid`):
проверенный отказ другой оплаты того же заказа его не глушит. Отметку
«отклонена» получают только погашенные оплаты (`cancelled`), не
возвращённые (`refunded`): там деньги ушли покупателю нашим путём.
Сотрудника с такой отметкой удалить навсегда нельзя — понятный отказ в
админке. Кнопку в админке добавит касса (этап 3).

**Тревога** — через Healthchecks, как у резервных копий (тревоги Grafana
строятся только по цифрам агентов на машинах, журналы приложения туда не
уходят — `deploy/monitoring/alerts.yaml`). Ночная сверка шлёт сигнал на
`MARKET_HC_PING_PAYMENTS`: без расхождений — «готово», с расхождениями —
«сбой» (`…/fail`), в теле — итог в цифрах («расхождений 2 (uzum 0, payme 1,
click 0, общее 1)»), без номеров и данных. Healthchecks шлёт тревогу в
Telegram и при сбое, и если сигнала не было вовремя (сверка не запустилась).
Настройка — `docs/monitoring.md`, шаг 3.

**Сверить с договорами и документацией** до включения на боевом: Uzum —
имена полей, коды, разрешён ли `reverse` подтверждённой транзакции, формат
ссылки на оплату; Payme — коды -31050…-31099, состав `detail` (`package_code`
— у товара его пока нет, TODO; ИНН продавца для маркетплейса), формат ссылки
checkout; Click — порядок полей подписи и формат `amount` в ней, ответ на
повторный Complete (0 или -4), что передавать в reversal (`click_paydoc_id`
или `click_trans_id`) и в какие сроки он возможен.

## Касса — этап 3

Код — `python/savdex/market/cash.py` (баланс, реквизиты, выплаты, ручной
возврат) и `cash_admin.py` (админка), схема —
`2026_11_21_120000_create_market_payouts.sql`, проверки —
`python/tests/test_market_cash.py`. Правила — `docs/marketplace-security.md`,
разделы 3 и 4. Выплата пока ручная (ТЗ: выплаты по оферте — позже):
продавец видит начисления в кабинете, касса переводит деньги платёжкой из
банка и отмечает это в админке.

**Роли** (`savdex/access.py`):

| Роль | Раздел | Может | Не может |
|---|---|---|---|
| Касса маркетплейса (`cashier`) | `market_cash` (m) | балансы, выплаты, сверка наличных с BTS, реквизиты (смотреть), ручной возврат | заказы, остатки, модерация, шаги заказа |
| Склад маркетплейса (`warehouse`) | `market_stock` (m), `market_orders` (r, без сумм) | шаги заказа: в сборку → отгружен → в пункте → выдан | отменить заказ, деньги, выплаты, продавцы |

Шаги заказа в карточке заказа (`OrderAdmin`) доступны с `market_orders.moderate`
(администратор) или `market_stock.moderate` (склад); отмена — только
`market_orders.moderate`. Строка журнала шага складом — раздел
`market_stock`. Модератор, поддержка, финансы и администратор кассы не
видят (выплаты — только роль кассы; суперадмин — как всегда, всё).

**Баланс продавца** — из журнала денег, `seller_payable` по его заказам:

- начислено — по заказам, кроме отменённых, «ждёт возврата» и «деньги
  возвращены»;
- к выплате — только выданные (`issued`) больше N дней назад (настройка
  `market_payout_hold_days`, по умолчанию 7, не меньше 1 — срок на
  возврат); заказ «при получении» — ещё и только после отметки кассы
  «сверено с отчётом BTS» (`market_orders.cash_reconciled_at`, раздел
  «Наличные: сверка с отчётом BTS»). Номер или дата отчёта BTS —
  обязательно, не короче 10 знаков (`cash_reconciled_ref`), в пачке — один
  на всю пачку; пачкой — через страницу подтверждения (сколько заказов и на
  какую сумму), не больше 100 заказов за раз. Показанные цифры уходят
  скрытыми полями: сервер пересчитывает их под замком строк и при
  расхождении снова показывает подтверждение с новыми цифрами; строка журнала
  `cash_reconciled`. Сверку можно снять с причиной (`cash_unreconciled`),
  пока деньги заказа не ушли в выплату (снятие не уводит доступное в минус).
  Кто сверял наличные продавца, тот не подтверждает его выплату: заказы,
  сверенные этим кассиром после последней выплаченной выплаты, — отказ
  (выплата с заказами не связана — приближение);
- держится = начислено − к выплате; доступно = к выплате − выплаты в работе
  (создана, подтверждена) − выплаченное (не меньше нуля).

**Допущение:** деньги картой идут продавцу «к выплате» до того, как пришли
на наш счёт, — по проведённой оплате, без ночной сверки с выпиской банка.
Расхождение покажет сверка оплат (этап 2); выплату по нему касса не
отменит задним числом. Сверка с выпиской перед выплатой — следующим шагом.

**У своей компании не купить**: оформление (`orders.checkout`) отказывает
покупателю — сотруднику компании продавца (`order.own_company`, 422):
иначе продажи накручиваются и выводятся выплатой.

**Выплата — в два шага** (`market_payouts`: `draft → approved → paid`,
`draft | approved → cancelled`):

1. Кассир в «Балансы продавцов» создаёт выплату — не больше доступного,
   только при заполненных реквизитах и только подтверждённому продавцу
   (заблокированному — ни создать, ни подтвердить).
2. Другой кассир подтверждает (тот же — отказ; база держит
   `approved_by <> created_by`). Реквизиты сменены меньше 24 часов назад —
   только с отметкой «реквизиты сверены» и заметкой, как сверили (по
   известному телефону и т. п.); в выплате — `fresh_requisites` и
   `fresh_check_note`, заметка — и в журнале действий.
   Подтверждённые реквизиты запоминаются (`requisites_log_id`).
3. После платёжки — «Отметить выплаченной» с номером платёжного поручения:
   одна группа журнала денег `seller_payable +сумма / payout_clearing −сумма`
   (долг продавцу закрыт, деньги ушли с нашего счёта), ровно один раз —
   условным переходом `approved → paid` под замком; номер платёжки — один
   на выплату (уникальный индекс); доступное перепроверяется. Реквизиты
   сменились после подтверждения — отметить нельзя: отменить и создать
   заново.
4. Отменить созданную может любой кассир, подтверждённую — только тот, кто
   её подтвердил (или суперадмин), с отметкой «платёжка в банк не
   отправлялась» (`cancel_not_sent`) и причиной: иначе деньги ушли бы
   продавцу дважды.

Выплату не переписать и мимо кода: триггер `market_payouts_guard` не даёт
менять продавца, сумму и автора; переходы — только вперёд (draft →
approved | cancelled, approved → paid | cancelled); после ухода из draft не
меняется подтверждение (кто, когда, реквизиты, отметка «сверены»);
выплаченная и отменённая не меняются вовсе.

Замки везде в одном порядке: строка продавца, затем выплата. Каждое действие
— строка журнала действий (раздел `market_cash`: кто, что, сумма, продавец).

**Реквизиты** (`market_seller_requisites`, история —
`market_seller_requisites_log`, только дописывается, даже владельцу базы):
расчётный счёт 20 цифр, МФО 5 цифр, банк, получатель, ИНН (9) или ПИНФЛ
(14); управляющие и невидимые символы (категории Unicode Cc и Cf) в
названиях — отказ. Меняет только владелец компании из кабинета, повторно
введя пароль от входа; пять неверных паролей подряд — смена закрыта на
сутки (`market_sellers.requisites_locked_until`, ответ 429) и письмо
владельцам. Блок — на компанию-продавца, то есть сразу для всех её
владельцев, а не на одного: сознательно — подбор пароля одного владельца
не должен оставить открытой смену реквизитов через другого; у владельца без пароля — текст «задайте пароль в настройках»
(TODO: код на почту). Каждая смена — строка истории и уведомление
владельцам на языке каждого (`users.locale`; лента кабинета и письмо, без
самих реквизитов: «реквизиты изменены, если это не вы — напишите в
поддержку»; сбой письма — в журнал приложения, запрос не падает; TODO —
и на прежнюю почту, когда появится история её смены). В админке — только
смотреть, с историей смен (кто, когда, IP); в списке счёт скрыт (`•••• 1234`),
поиска по счёту нет.

**Наличные при выдаче.** Выдан заказ «при получении» — в той же транзакции,
что переход в `issued` (`orders.advance`), группа
`cash_collected +итого / buyer_receivable −итого`: долг покупателя закрыт
деньгами пункта выдачи. Сверка `cash_collected` с отчётом BTS — следующим
шагом (ночная сверка, как у оплат).

**Ручной возврат.** «Возвраты покупателям» — заказы в `refund_pending`. Где у
провайдера нет API возврата (Click без `MARKET_CLICK_MERCHANT_USER_ID`) или
отмена не пришла колбэком, касса возвращает деньги в кабинете провайдера и
отмечает здесь. Режим возврата — `market_payments.refund_mode`:

| Режим | Кто ставит | Отметить вручную |
|---|---|---|
| `api` | расписание — до сетевого вызова к провайдеру | нет: запрос в полёте |
| `manual` | расписание — API возврата нет | любой кассир |
| `error` | расписание — сбой связи, итог неизвестен | любой кассир |
| `claimed` | касса — «Беру возврат на себя», пока возврат не запрошен (`refund_claimed_by`) | только взявший или суперадмин |

`api` без итога дольше 15 минут по `refund_requested_at`
(`cash.API_STALE_MINUTES`: процесс упал посреди вызова) считается `error` —
и в `cash.mark_refunded`, и в разделе возвратов; раньше суперадмин может
перевести его в `error` вручную, с причиной (журнал `refund_api_failed`).
**Каждая ветка `payments.base.refund_order` обязана выставить
`refund_mode`** (api до вызова, затем manual, error или сброс при отказе):
режим без итога касса не отличит от запроса в полёте.

Взятие снимает только суперадмин, с причиной (журнал `refund_unclaimed`), —
с предупреждением: если деньги уже вернули в кабинете, расписание вернёт их
ещё раз. После снятия возврат снова запросит расписание; пометка оплаты (`note`) дописывается, а
не затирается. Отметка — с номером возврата у провайдера
(`refund_reference`, один на возврат — уникальный индекс) и комментарием:
`payments.base.refund_payment` (оплата `paid → refunded`, заказ
`refund_pending → refunded`, проводка возврата — один раз) и строка журнала
`refund_marked` — одной транзакцией. Зависший возврат касса может отметить
«Проверено у провайдера» (`payments.base.acknowledge`: право, заметка не
короче 10 знаков, строка журнала `payment_checked` — там): сверка его
больше не показывает, заказ остаётся `refund_pending`.

**Кабинет продавца:**

| Метод | Адрес | Что |
|---|---|---|
| GET | `me/balance` | `{balance: {accrued, onHold, available, inWork, paid, holdDays, payouts: [{id, amount, status: {code, text}, bankReference, createdAt, paidAt}]}}` — только свой продавец (сотрудник компании тоже); не продавец — 403 |
| GET | `me/requisites` | `{requisites: {bankAccount, bankMfo, bankName, recipientName, recipientTin, changedAt} \| null}` — только владелец компании, иначе 403 |
| POST | `me/requisites` | `{bankAccount, bankMfo, bankName, recipientName, recipientTin, password}` → `{message, requisites}`; ошибка — 422 по полям (неверный пароль — поле `password`); CSRF, не чаще 10 раз в час; каждая смена — строка истории и уведомление владельцам |

## Адреса для страниц — `/market/api/…`

Ответ — JSON. Языковой префикс работает как у страниц:

**Без входа (GET):**

уменьшенная копия первого общего фото (480 px).

**Со входом.** Гость получает `401 {message, login}`; адрес страницы, с
которой он пришёл, запоминается — после входа он вернётся к товару. Запись —
POST с токеном CSRF в заголовке `X-XSRF-TOKEN` (как шлют Inertia и axios).
Ошибка проверки — `422 {message, errors: {поле: [текст]}}`.

| Адрес | Что |
|---|---|
| GET `cart` | `{parts: [{seller, items, total}], count, lines, total}` |
| POST `cart/add` `{variantId, quantity}` | положить; больше остатка — 422 «В наличии только N шт.» |
| POST `cart/<variantId>` `{quantity}` | сколько штук, 0 — убрать |
| GET `favorites` · POST `favorites/<productId>` | список номеров · в избранное и обратно |
| GET `me/seller` | статус заявки, `checks` (компания, владелец, ИНН, документы), `canApply` |
| POST `me/seller/apply` `{offer: true, note}` | заявка «Стать продавцом» |
| GET `me/products` | «Мои товары» (только подтверждённому продавцу, иначе 403) |
| POST `me/products/create` | новый товар — черновик |
| GET · POST `me/products/<id>` | товар для формы · сохранить правку |
| POST `me/products/<id>/submit` | «Отправить на продажу»: `pending` (на проверку) или `active`; не хватает полей — 422 и `missing` |
| POST `me/products/<id>/hide` | снять с продажи |
| POST `me/products/<id>/images` (multipart: `file`, необязательно `variantId`) · POST `…/images/<imageId>/variant` `{variantId: номер \| null}` · POST `…/images/<imageId>/delete` | добавить фото (WebP до 1600 px и копия 480 px, без EXIF; с `variantId` — фото этого варианта) · сделать фото варианта или общим · удалить (оба файла) |

Тело товара:

```json
{
  "title": "Курага сушёная, 1 кг",
  "description": "…",
  "category": "dried-fruits-nuts",
  "locale": "ru",
  "ikpu": "12345678901234567",
  "barcode": "4600000000000",
  "weight_g": 1000, "length_mm": 200, "width_mm": 150, "height_mm": 50,
  "values": {"color": "black", "memory": 128},
  "variants": [{"id": 5, "options": {"Цвет": "Чёрный"}, "sku": "A-1", "price": 125000, "oldPrice": 150000, "active": true}]
}
```

Категория — самая точная, без подразделов. Вариант без `id` — новый;
вариант, которого нет в списке, убирается: выключается и помечается, но не
удаляется — на него будут ссылаться заказы; его фото становятся общими, из
корзин он уходит. Характеристика «да / нет» принимает `true` / `false`,
`1` / `0`, «да» / «нет» и отдаётся в форме правки как `true` / `false`, в
карточке — «Да» / «Нет», в фильтре — `attr.<код>=1`.

## Свой адрес — `MARKET_DOMAIN`

Адрес маркетплейса (`market.savdex.uz`, на тестовом —
`market.staging.savdex.uz`) приходит сайту в переменной `MARKET_DOMAIN`
(её пишут `deploy.sh` и `prod-app.sh`, `deploy/README.md`). Нет
переменной — всё как раньше, маркетплейс по адресам `/market/…`. Код —
`python/savdex/market/domain.py`.

- **На адресе маркетплейса страницы — с корня:** `/` — главная, `/catalog`,
  `/product/<адрес>`, `/cart`, `/uz/cart` и т. д. Внутри это те же виды
  `/market/…`, адрес страницы при этом остаётся корневым. Старый вид
  `/market/…` — переход на корневой (302).
- Вход, регистрация, сброс пароля, язык, файлы и `/market/api/…` — как
  есть, на обоих адресах. Прочие страницы основного сайта — переход на
  основной адрес (302): каталог объявлений и компании вторым экземпляром не
  живут.
- **На основном адресе** страницы `/market/…` переходят на адрес
  маркетплейса (JSON — нет).
- **Один вход:** кука сессии — на общий домен двух адресов (`.savdex.uz`,
  на тестовом — `.staging.savdex.uz`). Имя такой куки — с окружением:
  `savdex-production-session`, `savdex-staging-session` — кука боевого не
  смешивается с кукой тестового. При первом включении все выходят один
  раз: у куки новое имя. `XSRF-TOKEN` остаётся кукой своего адреса.
  `SESSION_DOMAIN` и `SESSION_COOKIE`, если заданы, — главнее.
- Страницам — общий проп `marketLinks`: `base` — с чего начинаются адреса
  страниц маркетплейса здесь (`""` на его адресе, `"/market"` на
  основном), `site` — основной сайт, `market` — адрес маркетплейса или
  `null`. Ссылки фронтенда пока ведут на `/market/…` — на адресе
  маркетплейса они работают через переход; с `base` перехода не будет.
- На боевом общая кука включится вместе с `MARKET_DOMAIN` при запуске —
  до этого решить вместе с Жавохиром.

## Как проверить у себя

```bash
cd python
uv sync --all-groups
uv run ruff check . && uv run ruff format --check . && uv run mypy savdex
SAVDEX_PARITY_PG_URL=postgres://…/savdex_test uv run pytest -q tests/test_market.py
```

На тестовом стенде после выкладки: `manage.py schema` применит миграцию
сам (категории появятся вместе с ней), `manage.py seed` заведёт настройку
«Первые товары нового продавца».

**Демо-товары на тестовом** — `manage.py demo` (`savdex/market/demo.py`):
8 продавцов и 12 товаров из `demo.ts` Максуда, в продаже, с вариантами,
характеристиками и сводкой цены; фото нет, как и в `demo.ts`; ИКПУ
придуманные (начинаются с `99`). Добавляется и к базе, где демо SavdEx
уже есть, — ничего не стирает; повторный запуск ничего не дублирует; на
боевом (`APP_ENV=production`) — отказ. Сброс тестового на демо-данные
(`staging-reset.sh`) заводит их сам.
